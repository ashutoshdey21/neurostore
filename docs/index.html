neurostore

A small store for multi-channel electrophysiology recordings and the brain-stimulation events inside them. Write a recording, mark its TMS pulses, then pull back time windows or event-locked epochs, with every read and write logged.

Python 3.11+ numpy · sqlite3 ~500 lines of source 41 tests

The package answers three questions a lab asks of its recordings: what do we have (list_recordings), what happened between these two times (get_window), and what does the brain do right after each stimulus (get_epochs). Everything else supports those three: validation on the way in, a checksum on the way out, and an audit trail of who did what.

from neurostore import Event, Role, Store

store = Store(Path("my_store"), actor="alice", role=Role.READ_WRITE)
session = store.add_session(store.add_subject(), datetime.now(UTC), protocol="sp_tms")
rec = store.add_recording(session, signal, 250.0, channels, datetime.now(UTC))
store.add_events(rec, [Event("tms_pulse", t, {"intensity_pct": 110.0}) for t in (5, 20, 40)])

epochs, skipped = store.get_epochs(rec, "tms_pulse", pre_s=0.1, post_s=0.3)
evoked = epochs.mean(axis=0)   # (channels, samples)
Data model

Four entities, each owned by the one before

A subject has sessions, a session has recordings, and a recording has events. Only the recording carries signal data. IDs are random UUIDs, so they reveal nothing about the person or the order of enrolment.

Subject

root
  • id (UUID)

Nothing else. No name, birth date, or notes field.

Session

→ subject
  • start_time (UTC)
  • protocol label

Recording

→ session
  • channels
  • fs (Hz)
  • start_time (UTC)
  • n_samples
  • path + sha256

Event

→ recording
  • type, e.g. tms_pulse
  • t (s from start)
  • params, e.g. intensity_pct
Architecture

A database for facts, files for samples

A store is one directory. neurostore.db is a SQLite file with the metadata, events, and audit log. signals/ holds one .npy file per recording, shaped channels × samples, float32. The database row for a recording points to its file by relative path and stores the file's SHA-256.

my_store/
├── neurostore.db           subjects · sessions · recordings · events · audit_log
└── signals/
    ├── 3f0c…e1.npy          float32, (channels, samples), written once
    └── 9a72…4b.npy

Every public method follows the same path:

check role→ validate input→ read or write→ verify checksum (reads)→ append audit row

The code is split in two. models.py holds the data types, error classes, and validation rules, with no I/O. store.py holds the SQLite schema and the Store class. Writes put the audit row in the same transaction as the data, so a write and its log entry succeed or fail together. If the database insert for a recording fails, its .npy file is removed again.

Errors are specific classes: ValidationError, AccessDeniedError, ChecksumError, and NotFoundError, all under NeurostoreError. Messages say what was wrong and what was expected, for example channel count mismatch: 2 names for 3 signal rows.

Time and samples

Where a window starts and stops

Off-by-one errors are the classic bug in this kind of code, so the rule is fixed and tested. A time t maps to sample round(t × fs). A window [t_start, t_end) includes its start sample and excludes its end sample. Rounding, rather than truncating, matters because 0.1 × 100 is 10.000000000000002 in floating point.

Epochs use the same rule. An epoch spans [event − pre_s, event + post_s), so every epoch has exactly round(pre_s·fs) + round(post_s·fs) samples and they stack into one array. An event whose epoch would start before sample 0 or end past the last sample is skipped and counted.

Design decisions

Integrity, audit, and privacy

Why SQLite plus .npy

Metadata and events are small and relational: you filter by subject, protocol, and event type. Signals are large dense arrays read in bulk. SQL suits the first and a flat binary file suits the second. Both are single files, need no server, and come with Python and numpy, so the store can be opened anywhere.

Why the checksum

The database and the signal files can drift apart: a file is overwritten, half-copied, or edited by another tool. The SHA-256 recorded at write time is checked on every read, so a single changed sample raises ChecksumError before any analysis runs on it. A test edits one value in a file and checks that both window and epoch reads refuse it.

Why the audit log

With human-subject data you need to be able to say afterwards who read or changed what, and when. Every method appends (actor, action, object_id, UTC time). Writes log in the same transaction as the data. Denied write attempts are logged too, as add_subject:denied.

Privacy-related choices

Subjects are bare UUIDs. Protocol labels, event types, and parameter names must match [A-Za-z0-9_.-]{1,64}, so no field can hold free text like a name or a clinical note. The de-identified export drops internal IDs, file paths, and absolute start times; event times stay relative to the start of the recording. These are design choices. They do not on their own make data de-identified.

Roles

A store opens read-only unless you ask for Role.READ_WRITE. The caller declares the role, so it prevents accidental writes, not deliberate misuse.

Scope

Left out on purpose

Each of these would be needed in a real system. They were left out to keep the sample small and the core paths easy to read.

  • Update and deleteRecordings are append-only. Changing a recording in place would silently change the data earlier analyses used, and a delete has to remove the file, the rows, the events, and keep an audit entry, all consistently. A real system needs deletion at least for consent withdrawal: an audited, admin-only hard delete, with corrections stored as new versions instead of edits.
  • Memory-mapped or partial readsget_window loads the whole file, verifies the checksum over all of it, then slices. That is fine for minutes of 8-channel data. A one-hour, 256-channel, 2 kHz float32 recording is about 3.7 GB, and you would not want to read it all for a two-second window. The fix is chunked storage (HDF5 or Zarr) with a checksum per chunk, so a read touches and verifies only the chunks it needs.
  • Concurrent writersSQLite allows one writer at a time. Two processes writing at once will wait, then fail with database is locked. There is no WAL mode, retry, or busy timeout configured. UUID file names do prevent two writers from overwriting each other's signal files. Multi-user use would move metadata to Postgres.
  • A command-line interfaceThe package is Python-only. Commands like neurostore ingest, list, and export would be a thin wrapper over the same methods, but the spec asked for a library.
Known gaps

What would change for real clinical data

This package is not suitable for real patient data as it stands.

  • Encryption at rest, with managed keys. Today the database and signals are plain files.
  • Real authentication and authorization. Actor and role should come from an identity provider and be enforced outside the client process.
  • A tamper-evident audit log in an append-only store that users cannot edit.
  • Formal de-identification review. Signals, event timing, and metadata can still identify someone.
  • Institutional compliance review: IRB, data-use agreements, and the institution's security and privacy offices.
  • Scalable storage: HDF5 or Zarr for chunked signals, Parquet for events and exports, Postgres for multi-user metadata.
  • Standard formats: BIDS (EEG and iEEG) and EDF/EDF+ import and export.
